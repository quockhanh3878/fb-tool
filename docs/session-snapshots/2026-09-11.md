## Đánh giá đề xuất "liên kết clone với Profile Chrome thay vì nạp cookie" (chỉ khảo sát, chưa sửa mã)

### Phát hiện trong mã (đối chiếu thật)
- **nặng** — Đường backend (dashboard + desktop): cookie nạp vào được giải mã rồi ghi **plaintext** ra `<profile>/cookies.json` (`browser_runtime.write_cookie_file`), nhưng **không có mã nào đọc file đó** (không có `add_cookies` ở đâu cả). Worker mở `launch_persistent_context` trên thư mục profile trống → nick mới chưa từng đăng nhập. Cookie chỉ đang dùng làm cổng state machine `ONBOARDING -> WARMING_UP` + đọc hạn cookie.
- **nặng** — Backend không có luồng đăng nhập tay; chỉ CLI có `BrowserManager.login_interactive` (mở profile qua tool, cùng vân tay, chờ Enter).
- **vừa** — `warmup_task` gọi `create_stealth_context(headless=True)`, trái quyết định "không headless".
- **vừa** — `BROWSER_CDP_ENDPOINT` là cấu hình toàn cục: bật lên thì MỌI clone attach chung 1 Chrome.

### Đính chính đề xuất
- Không trỏ được vào `Chrome\User Data\Profile X` hằng ngày: Chrome 136+ bỏ qua remote debugging (port lẫn pipe Playwright dùng) trên thư mục dữ liệu mặc định; copy riêng thư mục profile sang chỗ khác thì cookie mất (mã hoá gắn với `Local State`). Phải đăng nhập bên trong thư mục do tool sở hữu (`browser_profile_path` đã có).
- Đăng nhập phải qua CHÍNH tool mở profile (cùng vân tay + proxy); đăng nhập bằng Chrome trơn rồi worker mở lại với vân tay spoof = lệch môi trường.
- Đăng nhập xong không được nhảy thẳng Active — phải vào `WARMING_UP` (không bỏ warm-up).
- CDP mỗi clone 1 cổng: không proxy + không vân tay (quy tắc attach) -> nhiều nick cùng IP nhà; cổng debug mở = tiến trình local nào cũng điều khiển được phiên FB. Chỉ hợp cho 1 nick chính / dev.
- Nút "Mở trình duyệt đăng nhập" chỉ có nghĩa ở chế độ desktop (SaaS thì browser mở trên server).

### Bước nhỏ tiếp theo
